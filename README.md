# @1chat/agent

Будит вашего ИИ-агента, когда в [1-chat](https://1-chat.ru) приходит сообщение,
собирает сообщения в пачки и не даёт агенту отправить устаревший ответ.

```bash
export ONECHAT_API_KEY=sk_1chat_rw_...
npx @1chat/agent --agent "1chat-hermes-bridge"
```

Нужен Node.js 22.13 или новее: состояние хранится во встроенном SQLite.

## Зачем

Человек пишет мысль несколькими сообщениями:

> Напиши Денису
> что сегодня не получится
> хотя погоди, завтра утром получится

Если будить агента на каждое сообщение, он ответит на первое, пока человек
дописывает второе, и Денис получит «сегодня не получится». Эта служба:

1. **Собирает пачку.** Агент запускается, когда человек замолчал на 3 секунды,
   но не позже 15 секунд от первого сообщения пачки.
2. **Не даёт устаревшему запуску действовать.** Если уточнение пришло, пока
   агент работал, его отправка не проходит: локальный MCP отвечает
   `STALE_CONTEXT` и в 1-chat ничего не уходит.
3. **Запускает заново со всей пачкой.** Следующий запуск получает исходное
   поручение вместе с уточнением, а не одно «хотя погоди».

```
1-chat ──лента──▶ приём ──SQLite──▶ диспетчер ──stdin──▶ bridge ▶ агент
                                                                   │
1-chat ◀──ключ── защищённый MCP (127.0.0.1) ◀──пароль запуска────┘
```

Приём ленты не ждёт агента. Ключ 1-chat есть только у службы; агент ходит
в 1-chat через локальный MCP с паролем, который действует только на время
своего запуска.

## Пачки и очередь

| Параметр | По умолчанию | |
|---|---|---|
| `--quiet-ms` | `3000` | пауза после последнего входящего |
| `--max-wait-ms` | `15000` | максимум от первого сообщения пачки |
| `--concurrency` | `2` | запусков одновременно, всего |
| `--run-timeout-ms` | `300000` | предел одного запуска |
| `--max-attempts` | `3` | попыток на пачку при ошибках |
| `--mcp-port` | `8765` | порт локального MCP, только `127.0.0.1` |
| `--db` | `.state/agent.db` | база состояния |
| `--dialogs <id,id>` | все | реагировать только на эти диалоги |
| `--from now\|begin` | `now` | с чего начать при первом запуске |

- Каждое новое сообщение сбрасывает паузу, но не начало пачки: человек,
  пишущий без остановки, всё равно получит ответ.
- В одном диалоге не бывает двух активных запусков. Разные диалоги друг друга
  не ждут, вместе их не больше `--concurrency`.
- Максимальное ожидание разрешает только **начать готовить** ответ. Отправка
  всё равно ждёт паузу и проходит проверку актуальности.
- Если запуск устарел, окно максимального ожидания отсчитывается заново, а
  пачка остаётся целой. Иначе при непрерывном вводе устаревшие запуски шли бы
  по кругу, и каждый стоил бы модели токенов.

## Защита действий

Каждый запуск получает свой `run_id`, снимок версии диалога `input_version`
и свой пароль к локальному MCP (`ONECHAT_MCP_TOKEN`). Версия диалога растёт с
каждым новым или исправленным входящим.

Перед каждым изменяющим вызовом служба проверяет:

1. пароль принадлежит запуску, и запуск ещё идёт;
2. версия **диалога поручения** не изменилась. Проверяется именно он, даже если
   сообщение отправляется в другой диалог: «Напиши Денису» проверяется по
   диалогу, где это попросили;
3. после последнего входящего прошла пауза. Если нет, вызов ждёт и проверяет
   версию снова;
4. инструмент разрешён;
5. то же действие в этой пачке ещё не выполнялось.

Проверка и регистрация действия идут одной транзакцией в том же процессе, что
и приём ленты, так что новое сообщение между ними вклиниться не может. Сетевой
вызов делается уже после транзакции.

| Ответ инструмента | Что значит | Что делать агенту |
|---|---|---|
| `STALE_CONTEXT` | пока агент работал, собеседник написал ещё | ничего, завершиться; служба запустит заново |
| `ALREADY_DONE` | такое же действие уже выполнено в этой пачке | не повторять |
| `UNCERTAIN_RESULT` | ответ 1-chat потерян, действие могло выполниться | не повторять; служба сверит историю |
| `RUN_NOT_ACTIVE` | запуск завершён или истёк | ничего |
| `ACTION_NOT_ALLOWED` | инструмент запрещён в этом режиме | — |
| `UNAUTHORIZED` | изменение без пароля запуска | — |

### Инструменты

Список закрытый: всё, чего в нём нет, запрещено. Новый инструмент на сервере
не станет обходом защиты.

- **Только чтение**, с любым действующим паролем: `list_conversations`,
  `get_conversation`, `list_messages`, `list_participants`, `list_accounts`,
  `search_recipients`, `list_webhooks`.
- **Под проверкой**, только с паролем запуска: `send_message`, `set_reaction`,
  `remove_reaction`, `mark_conversation_read`, `start_conversation`.
- **Запрещены**: `register_webhook`, `wait_for_changes` и любые неизвестные.
  В `tools/list` агент их не видит. Пакетные JSON-RPC-запросы отклоняются.

`client_id` отправки назначает служба, а не модель: по нему сверяется
неопределённый результат.

### Граница гарантии

Служба узнаёт об уточнении, когда оно пришло из ленты 1-chat, обычно в
пределах секунды. **Если отправка уже началась до этого момента, отменить её
нельзя**: сообщение уже в пути. Пауза перед отправкой (3 секунды) делает это
окно маленьким, но не нулевым.

Защита работает только для действий через локальный MCP. Если у агента есть
другой путь в мессенджер (свой бот, терминал с `curl` и ключом), служба его
не видит.

## Ошибки и восстановление

Завершение процесса и выполнение задачи — разные вещи:

| Исход | Статус запуска | Пачка |
|---|---|---|
| код 0, версия не менялась | `succeeded` | разобрана |
| код 0 или ошибка, но пришло уточнение | `stale` | остаётся, следующий запуск получит всё; попытка не тратится |
| ненулевой код | `failed` | повтор через 10 с, 1 мин, 5 мин |
| таймаут | `timed_out` | SIGTERM всей группе процессов, через 5 с SIGKILL выжившим; повтор |
| команда не запустилась | `spawn_failed` | повтор |
| служба остановлена или упала | `interrupted` | повтор после старта; пароль запуска сразу недействителен |

Запуск считается законченным, только когда в его группе процессов никого не
осталось. Фоновые процессы, брошенные агентом, завершаются вместе с запуском и
не работают параллельно со следующим.

После `--max-attempts` неудач пачка признаётся брошенной (об этом пишется в
лог), чтобы диалог не застрял навсегда. Немедленных перезапусков не бывает.

**Действия** записываются до вызова и после ответа. Если ответ потерян при
отправке сообщения, результат — `uncertain`, и слепого повтора нет:

- служба ищет своё `client_id` в истории диалога. Нашла — отправка
  засчитывается как выполненная;
- не нашла раньше чем через 3 минуты — результат по-прежнему неизвестен,
  потому что сообщение может быть в пути (сервер ждёт мессенджер до 130 с);
- не нашла позже — отправка признаётся невыполненной, и её можно повторить.

Отправка, начатая в момент падения службы, после перезапуска считается
`uncertain`.

**Exactly-once не обещается.** Сервер 1-chat не отсекает повторы по
`client_id`, поэтому гарантия — «не дублировать при известных сбоях», а не
«ровно один раз при любых».

После рестарта ничего не теряется: курсор и принятые сообщения пишутся одной
транзакцией, незавершённые пачки дожидаются запуска. Одно и то же сообщение
приходит в ленте несколькими событиями (создано, затем обновления статуса),
и работу по нему создаёт только первое. Дедупликация идёт по идентификатору
сообщения и отпечатку его содержания.

## Контракт запуска

Команда `--agent` получает в stdin JSON:

```json
{
  "contract": "1chat.agent.run/v1",
  "run_id": "5b0c…",
  "dialog_id": "266fd205-…",
  "channel": "telegram_client",
  "input_version": 3,
  "attempt": 1,
  "reason": "new_messages | context_changed | retry",
  "created_at": "2026-09-14T10:00:03.000Z",
  "deadline_at": "2026-09-14T10:05:03.000Z",
  "messages": [
    { "id": "…", "conversation_seq": 12, "direction": "inbound", "sender_name": "Даниил", "text": "Напиши Денису", "at": "…", "feed_seq": 7101 },
    { "id": "…", "text": "что сегодня не получится", "feed_seq": 7102 },
    { "id": "…", "text": "хотя погоди, завтра утром получится", "feed_seq": 7104 }
  ],
  "previous_actions": [
    { "action_id": "…", "run_id": "…", "tool": "send_message", "target_id": "…", "arguments": { "text": "…" }, "status": "succeeded | failed | uncertain", "result": {}, "error": null, "started_at": "…" }
  ],
  "previous_runs": [{ "run_id": "…", "input_version": 1, "status": "stale", "exit_code": 0 }],
  "context": { "recent_messages": [], "recent_actions": [] },
  "mcp": { "url": "http://127.0.0.1:8765/mcp", "token_env": "ONECHAT_MCP_TOKEN" },
  "rules": ["…"]
}
```

- `messages` — вся необработанная пачка в порядке поступления.
- `previous_actions` — что уже сделано по этой пачке прошлыми запусками.
- `context` — последние уже обработанные сообщения и действия диалога.

Переменные окружения запуска: `ONECHAT_MCP_URL`, `ONECHAT_MCP_TOKEN`,
`ONECHAT_RUN_ID`, `ONECHAT_DIALOG_ID`, `ONECHAT_CONTRACT`. **`ONECHAT_API_KEY`
агенту не передаётся**, как и любая переменная, содержащая ключ.

Код выхода 0 означает, что пачка разобрана. Ненулевой — что работа не сделана.

## Hermes Agent

В пакет входит адаптер `1chat-hermes-bridge`. Он собирает запрос из контракта
и запускает Hermes разовым запросом:

```
hermes chat --oneshot -Q --query-file -
```

Текст запроса уходит в stdin, без shell. Код выхода Hermes становится кодом
выхода адаптера, а SIGTERM передаётся Hermes.

**`~/.hermes/config.yaml`** — пароль берётся из окружения запуска:

```yaml
mcp_servers:
  1chat:
    url: "${ONECHAT_MCP_URL}"
    headers:
      Authorization: "Bearer ${ONECHAT_MCP_TOKEN}"
    tools:
      include:
        - list_conversations
        - get_conversation
        - list_messages
        - list_participants
        - list_accounts
        - search_recipients
        - send_message
        - set_reaction
        - remove_reaction
        - mark_conversation_read
        - start_conversation
```

**Проверьте на сервере до включения:**

1. `hermes --version` и `hermes chat --help`: должны быть `--oneshot`, `-Q`,
   `--query-file`. Если флаги другие, задайте их явно:
   `HERMES_ARGS='["chat","-q","…"]'`; путь к бинарю — через `HERMES_BIN`.
2. Подстановка `${VAR}` в `url` и `headers` MCP-серверов описана в документации
   Hermes, но появилась не во всех версиях. Проверка: без службы вызов из
   Hermes должен получить отказ `401`, а не пройти.
3. **Не кладите `ONECHAT_MCP_TOKEN` и `ONECHAT_MCP_URL` в `~/.hermes/.env`.**
   По документации Hermes значения из `.env` важнее окружения процесса, и
   тогда вместо пароля запуска будет подставлено что-то постоянное:
   отправки перестанут проходить.
4. **Запускайте службу от отдельного пользователя ОС.** Процесс того же
   пользователя может прочитать окружение службы (`/proc/<pid>/environ`), а в
   нём ключ 1-chat. Если у Hermes есть терминал, без отдельного пользователя
   защита отправки обходится.
5. Если у Hermes есть свои инструменты для мессенджеров, отключите их для
   этого профиля: иначе у агента есть путь в обход проверки.

Для работы с Hermes вне запусков, вручную, есть пароль только на чтение:
`.state/agent.db.read-token`.

## Сокращение ответов

Сервер отдаёт агенту то же, что интерфейсу. Служба сокращает ответы
локального MCP, контракт и события:

- аватарки в base64 выбрасываются. На реальных данных это 91% объёма
  `list_conversations`;
- любое другое двоичное поле заменяется пометкой `[двоичные данные опущены]`,
  чтобы модель знала, что вложение было;
- выбрасываются `tenant_id`, `metadata`, пустые значения, служебные
  идентификаторы, дубли `settings`/`health`;
- вместо трёх отметок времени у сообщения остаётся одна, `at`;
- `structuredContent` убирается: сервер кладёт туда ту же строку, что в `text`,
  и модель получала каждый ответ дважды.

| | было | стало |
|---|---|---|
| `list_conversations`, 5 диалогов | 166 КБ | 5.6 КБ |
| `get_conversation` | 38 КБ | 0.7 КБ |
| `list_messages`, 20 сообщений | 33 КБ | 7.8 КБ |
| лента, 40 событий | 234 КБ | 25 КБ |

Идентификаторы, нужные для следующего вызова, и `client_id` остаются.

Сокращение делает пакет. Кто подключается к MCP 1-chat напрямую, получает
полный ответ.

## Переход со старого режима

Было:

```bash
npx @1chat/agent --exec "hermes run" --serve-mcp
```

Стало:

```bash
npx @1chat/agent --agent "1chat-hermes-bridge"
```

1. Остановите старую службу.
2. Обновите `~/.hermes/config.yaml`, как в разделе про Hermes. Постоянный пароль
   `.state/cursor.mcp-token` больше не нужен.
3. Запустите с `--agent` из той же рабочей папки. Курсор из `.state/cursor`
   будет перенесён в базу один раз, а файл переименован в `cursor.migrated`.
   Сообщения, пришедшие за время остановки, не потеряются.

`--agent` нельзя сочетать с `--exec` и `--serve-mcp`: так новый режим не может
случайно запуститься без защиты отправки.

## Старый режим

`--exec` и `--serve-mcp` работают, как в 0.2: запуск на каждое входящее, простой
MCP с постоянным паролем. Защиты от устаревшего ответа в этом режиме нет, при
запуске печатается предупреждение. Ответы сокращаются и здесь.

## systemd

```ini
[Unit]
Description=1-chat agent
After=network-online.target
Wants=network-online.target

[Service]
User=onechat
Environment=ONECHAT_API_KEY=sk_1chat_rw_...
WorkingDirectory=/opt/onechat
ExecStart=/usr/bin/npx -y @1chat/agent --agent "1chat-hermes-bridge"
KillMode=mixed
TimeoutStopSec=15
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`User=` должен отличаться от пользователя, под которым Hermes работает с
терминалом (см. раздел про Hermes, пункт 4). Если Hermes должен работать под
тем же пользователем, что и служба, закройте ему доступ к терминалу.

```js
import { OneChatClient } from '@1chat/agent'

const client = new OneChatClient({ apiKey: process.env.ONECHAT_API_KEY })
await client.run({
  since: null,
  onPage: async ({ cursor, events }) => {
    // сохраните события и курсор одной транзакцией
  },
})
```

## Ограничения

- Отправку, начатую до того, как служба узнала об уточнении, отменить нельзя.
- Exactly-once нет: у сервера 1-chat нет идемпотентности отправки.
- Будит только входящее. Ответ оператора из интерфейса во время работы агента
  контекст устаревшим не делает.
- Правка уже обработанного сообщения агента не будит.
- На первой версии служба ждёт завершения устаревшего процесса, а не убивает
  его. Отправки такого процесса заблокированы.
- Действия через другие каналы агента служба не контролирует.
